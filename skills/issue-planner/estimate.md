# Оценка sub-issue: LOC → размер → минуты

Оценка должна опираться на **историю PR этого репозитория**, а не на догадку.

## Шаг 1. Снять калибровку с git (делать в начале триажа)

```bash
gh pr list --state merged --limit 30 --json number,title,additions,deletions \
  --jq '.[] | "\(.additions + .deletions)\t\(.title)"' \
  | awk -F'\t' '{
      t=$2; sz=$1; type="other";
      if (t ~ /^feat/) type="feat"; else if (t ~ /^fix/) type="fix";
      else if (t ~ /^perf/) type="perf"; else if (t ~ /^refactor/) type="refactor";
      else if (t ~ /^test/) type="test"; else if (t ~ /^chore/) type="chore";
      else if (t ~ /^ci/) type="ci";
      sum[type]+=sz; n[type]++ }
    END { for (k in sum) printf "%-10s n=%-3d avg≈%d\n", k, n[k], sum[k]/n[k] }' | sort
```

Типичные веса для tg_content_factory (на 2026-06, проверять заново — могут дрейфовать):

| Тип PR | LOC (диапазон) | код/тесты |
|--------|----------------|-----------|
| Микро-fix / экстракция | 50–150 | 80/20 |
| Простой fix/alert | 150–300 | 56/44 |
| Рефактор (complexity drop) | 200–500 | 75/25 |
| Простая Web-фича (без DB) | 150–350 | 65/35 |
| PERF/DB (PRAGMA/index) | 150–300 | 50/50 |
| Стандартная фича (все слои parity) | 600–1200 | 64/36 |
| Крупная фича (+миграция данных) | 1500–2050 | 36/64 |

**Главный множитель этого проекта — parity.** Новая команда требует CLI + Web + Agent + tests одновременно → ×2–4 к голому коду. Проект тяжёл на тестах (60–67% диффа крупных фич). Новый agent-tool = +3 файла гейтов + snapshot/permissions.

## Шаг 2. LOC → t-shirt

- **S** < 100 LOC
- **M** 100–300
- **L** 300–600
- **XL** 600–1200
- **XXL** > 1200 (миграция / новый компонент)

## Шаг 2.1. Лимит размера PR: ~1000 строк (soft target)

**PR > 1000 строк (additions + deletions) — старайся не делать.** Большой PR:
- невозможно осмысленно отревьюить (reviewer пропускает баги — подтверждено на практике),
- ломает параллельную работу (cli.py-конфликты, длительные ребейзы),
- дольше висит, копит drift против main.

**Правило:** если оценка подзадачи → PR > 1000 строк:

1. **Разбить на части** — декомпозировать на 2+ независимых PR по ≤1000 строк
   каждый. **Предпочитай декомпозицию по фичам/tool'ам** (напр. 3 tool'а = 3 PR), не по
   слоям foundation (Tool-ABC + generalized CLI + migration — логически сцеплены, split
   делает части некомпилируемыми).
2. **Излишек, который нельзя разбить сейчас → follow-up issue.** Создать отдельный issue
   «Follow-up: <часть> (вынесено из #N — превышение лимита PR)», linked с родителем.
3. **Обоснованное исключение (НЕ нарушение):** если PR > 1000 потому что foundation
   неделим ИЛИ docs-sync CI gate требует docs идти с кодом (чистый src ≤1000, превышение
   за счёт docs+tests) — воркер **сам обосновывает неделимость** в комментарии к PR/issue
   и оставляет PR целиком. Это обоснованное исключение, эмпирический потолок ~1300-1500.
   НЕ эскалировать конфликт «лимит vs CI gate» как вопрос — решать через обоснование.

## Шаг 3. t-shirt → минуты агентной работы

Узкое место — итерации тестов/линта/правок, не печать. Минуты, НЕ часы (реализует агент).

| Размер | Минуты |
|--------|--------|
| S | 10–25 |
| M | 25–50 |
| L | 50–130 |
| XL | 100–180 |
| XXL | 180–300 |

**Множители:** +30% новый agent-tool (гейты+снапшоты), +20% горячий write-path / claim-гонка (concurrency-тесты), +25% требуется дизайн-решение до кода (investigation-first).

## Шаг 3.1. Оценка цикла review (цикл-проверка)

Каждый PR проходит `/cycle-review` (local `/review` + Codex adversarial, несколько
циклов пока clean). По факту review занимает **44–75% времени кода** — это не
учтено в Шаге 3, без него оценка систематически занижена.

Формула: **база (зависит от размера) + множитель security.**

### База (минуты review, один цикл)

| Размер | Циклов (ожидаемо) | База review (мин) |
|--------|-------------------|-------------------|
| S | 1 | 10 |
| M | 1–2 | 15–25 |
| L | 2–3 | 30–45 |
| XL | 3 | 45–60 |
| XXL | 3–4 | 60–80 |

### Множители security / сложности (аддитивно к базе)

Touch чего-либо из списка → множитель ×2 к базе review (Codex гоняет edge cases
до clean — это основная статья затрат):

- **Credentials / secrets** — чтение, маскинг, редакция в stdout/diff (credential
  disclosure — самый частый наход циклов review).
- **Файловые атомарные операции** — atomic rename, partial-activation recovery.
- **Concurrency / process lock** — flock, гонки, serialization.
- **Маркер-парсинг чужого содержимого** — `.zshrc` блоки, JSON deep-merge чужих
  ключей (fail-closed под malformed input).
- **Network probe** — HTTP-проверки endpoint'ов, offline-graceful.

Если ни одного множителя — база без умножения (чисто логический код).

### Пример

PR L (Claude Code `use zai`, touch credentials + marker-parsing + atomic writes):
- Код: ~90 мин (из Шага 3).
- Review база: 30–45 ×2 (3 security-множителя, но capped ×2) = **60–90 мин**.
- Итого: **150–180 мин** (факт ~150 — сходится).

## Шаг 4. Что писать в тело sub-issue

Блок «Оценка» в каждой sub-issue:

```
## Оценка
- **LOC:** ~<low>–<high> (src ~X / tests ~Y)
- **Размер:** <S|M|L|XL|XXL>
- **Время (код):** ~<low>–<high> мин
- **Время (review):** ~<low>–<high> мин  (база + ×2 если touch credentials/atomic/concurrency/marker/network)
- **Время (итого):** ~<low>–<high> мин
```

И сводный комментарий в эпик с таблицей всех sub-issues + суммарной оценкой + рекомендованным порядком (фундамент → параллельные слои → cleanup).

Сводная таблица в эпике — колонки: номер · подзадача · LOC · размер · **код мин** ·
**review мин** · **итого мин** · приоритет. Суммарная оценка = сумма «итого», НЕ
сумма «код» (иначе занижение на 44–75% из-за неучтённого review). Параллельные
слои уменьшают wall-clock, но не суммарную агентную работу.
