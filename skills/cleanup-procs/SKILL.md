# Чистка залежавшихся фоновых процессов

Инструмент: `cleanup_procs.sh` рядом с этим файлом (`~/.claude/skills/cleanup-procs/cleanup_procs.sh`).

## Проблема, которую решает

Claude Code / agent-orchestrator / Codex сессии при завершении **не убивают свои дочерние процессы**. Главные накопители (по наблюдениям на 24 GB Mac):

| Процесс | Что это | Почему висит |
|---------|---------|--------------|
| `context7-mcp` | MCP-сервер документации | переживает свою сессию, плодится десятками |
| `app-server-broker` | codex broker | остаётся с `PPID=1` после смерти сессии |
| `SkyComputerUseClient` | codex computer-use | хвосты `turn-ended` |

За несколько дней набегают **сотни процессов и гигабайты** — swap забивается под завязку (наблюдали 122 шт context7 = ~1.4 GB + 35 codex-брокеров), и параллельные воркеры начинают свопиться вместо работы.

## Безопасность (встроена в скрипт)

- **DRY-RUN по умолчанию** — без `--apply` только показывает кандидатов, ничего не трогает.
- **Фильтр по возрасту** (`--min-age`, дефолт 60 мин) — НЕ трогает свежие процессы, поэтому только что заспавненные живые сессии (`ao batch-spawn` минуту назад) в безопасности.
- **Защита своего PID-дерева** — никогда не убивает сам скрипт и его родителей.
- **SIGTERM**, не SIGKILL — мягкое завершение.

## Важно: только по явному запросу пользователя

Этот скилл вызывается **только** явной командой `/cleanup-procs` от пользователя
в моменте — `disable-model-invocation: true` запрещает модели подхватывать его
самостоятельно из контекста разговора (например, "перед батчем воркеров" или
"мало памяти"). Причина: `--apply` шлёт `SIGTERM` по паттерну command-строки и
возрасту процесса, а не по факту простоя — долгоживущий, но АКТИВНО работающий
агент/воркер (например, orchestrator-сессия, которая час крутит задачу в
worktree) может выглядеть "залежавшимся" и попасть под чистку. Прерывание
такого процесса SIGTERM'ом посреди git-операции наблюдалось как вероятная
причина повреждения orchestrator-worktree (см. issue #3265 в
Untrivial-ai/agent-orchestrator). Никогда не вызывай `cleanup_procs.sh`
(ни через этот скилл, ни напрямую через Bash) без свежего явного запроса
пользователя — даже если он выглядит уместным по контексту задачи.

## Как исполнять этот скилл

1. Сначала **dry-run** — показать пользователю, что найдено:
   ```bash
   ~/.claude/skills/cleanup-procs/cleanup_procs.sh
   ```
2. Перед `--apply` **всегда** спроси подтверждение — даже если пользователь
   уже когда-то просил «почисти» в этом разговоре; каждый запуск `--apply`
   требует отдельного согласия в моменте:
   ```bash
   ~/.claude/skills/cleanup-procs/cleanup_procs.sh --apply
   ```
3. Скрипт сам печатает сводку памяти/swap до и после — покажи пользователю дельту.

### Аргументы скилла → флаги скрипта

- пусто / `почисти` → dry-run, затем `--apply` после подтверждения
- `мем` / `память` → `--mem` (только сводка swap/PhysMem, без чистки)
- `порог N` → `--min-age N` (порог возраста в минутах; ниже 60 — осторожнее, можно задеть свежие сессии)

## Когда пользователь обычно просит это запустить

- Перед `ao batch-spawn` нескольких воркеров — расчистить память под параллелизм.
- Когда `vm.swapusage` показывает `used` близко к `total` и `PhysMem ... unused` < 500 MB.
- Периодически, если активно гоняешь сессии (мусор накапливается каждый день).

## Расширение

Новый тип залипающего процесса — добавь паттерн в массив `PATTERNS` в `cleanup_procs.sh`. Паттерн матчится по подстроке в `command`; фильтр возраста и защита PID-дерева применяются автоматически.
