# /test-categories — безопасный прогон тестов

Используй этот подход, когда инструкция «запусти тесты» может вызвать сеть,
авторизацию, запись в боевую БД, публикацию, отправку сообщения или другое
мутационное действие. Цель — сделать обычную команду тестов безопасной по
построению, а не надеяться на внимательность агента.

## Почему это проблема

Агент, которому сказано «при завершении запусти тесты», обычно выполняет это
буквально и добросовестно. Если тесты не заявляют о своей природе, bare test
command не может отделить проверку логики от необратимого действия в живом
аккаунте. Проблема не в дисциплине агента: чинить надо команду и harness, а не
воспитывать исполнителя.

Этот скилл переносит подход, проверенный в hhru (#217, PR #220 и исправление
аудита в #224), но не код hhru. Сначала исследуй текущий проект; не копируй
имена модулей, команды или конфигурацию из примера.

## 1. Быстрая диагностика

Ответь на вопросы до редактирования:

1. Какой test runner и какая голая команда используются локально и в CI?
2. Есть ли уже маркеры, tags, test groups или отдельные suites? Есть ли файлы
   без категории? Собери список тестовых файлов и мест, где категории задаются.
3. Какие тесты ходят во внешний сервис, даже если только читают? Ищи HTTP/SDK/DB
   клиенты, браузеры, очереди, коннекторы, login/auth и вызовы, создающие,
   меняющие или отправляющие данные.
4. Какой путь является фактической дверью наружу? Трассируй вызовы до самого
   низкоуровневого клиента/движка, а не только до удобной wrapper-функции.
5. Меняет ли обычный прогон реальные файлы, БД, аккаунт или логи?

Зафиксируй baseline: команда, число собранных тестов, live-тесты и побочные
артефакты до/после прогона. Не запускай обнаруженные live-write тесты во время
диагностики.

## 2. Категории и границы

Выбери нативный механизм runner-а (например, pytest markers, Jest projects,
JUnit tags или cargo features). Не изобретай вторую систему, если проект уже
имеет рабочую классификацию: найди и используй её. Минимальная переносимая
таксономия:

- `unit` — чистая логика, без внешней сети;
- `integration` — связка модулей с mock/fixture, без реального сервиса;
- `smoke` — короткая проверка сборки или CLI;
- `e2e` — сквозной сценарий на изолированных фикстурах;
- `live_read` — чтение реального сервиса, вне CI и обычного прогона;
- `live_write` — мутация только собственного пространства, обратимая и
  невидимая посторонним (например, временный черновик);
- `live_write_danger` — необратимая мутация или действие, которое видит другой
  человек/система (отправка, публикация, отклик, сообщение, удаление чужого).

Граница двух live-write категорий проходит не по факту «есть запись», а по
цене ошибки: кто видит результат и можно ли его корректно откатить. Если в
проекте уже описана граница READ/WRITE, найди её и следуй ей; не подменяй
доменную классификацию догадкой.

Каждый тестовый файл должен иметь ровно одну категорию. Если runner маркирует
тесты не на уровне файла, выбери эквивалентный инвариант (например, ровно один
project/tag на suite) и проверь отсутствие неразмеченных тестов.

## 3. Безопасный дефолт — главный рубеж

Измени конфигурацию так, чтобы голая команда тестов исключала все
`live_read`, `live_write` и `live_write_danger`. Она должна быть безопасной по
смыслу для агента и CI. Явный запуск live suite должен быть отдельной командой
с явным названием.

Проверь именно чистый путь, без специальных env/флагов: обычный runner, который
агент скопирует из инструкции. Убедись через collect/list/dry-run, что обычный
прогон не собирает live-тесты, а не только что они «обычно не падают».

## 4. Закрой фактическую дверь наружу

Добавь автоприменяемую заглушку или sandbox для всех тестов, кроме явно
разрешённых live-категорий. Патчить нужно низкоуровневую дверь (HTTP transport,
SDK client constructor, DB connector, browser engine и т.п.) и все способы
получить её:

- вызов через модульный атрибут;
- локальный импорт и ссылку, захваченную при импорте;
- алиасы в командах;
- альтернативные клиенты и прямой вызов движка.

Один wrapper может быть не единственной дверью. Напиши регрессионные тесты на
каждый найденный путь. Заглушка должна падать с понятной ошибкой и гарантировать,
что сеть/боевой ресурс не был достигнут. Не позволяй тесту снять защиту простой
подменой промежуточного атрибута.

Одновременно изолируй локальные побочные эффекты: временная БД/каталог/лог,
фикстуры и rollback. Сверяй состояние реальных данных до и после.

## 5. Permission-gate для опасных запусков

Сделай один короткий шлюз для `live_write_danger` и добавь для его точной
команды правило harness `ask` в проектные настройки (например,
`.claude/settings.json`). `ask` должен совпадать с вызовом шлюза, а не с широкой
командой вроде всего runner-а. Для безопасного `live_write` можно иметь
отдельный шлюз без ask, если его обратимость доказана.

Свойства шлюза:

- каждый вызов запускает только нужную live suite;
- каждое выполнение вызывает отдельный `ask` — разрешение не переносится на
  следующий запуск;
- отказ происходит до выполнения теста и означает ноль live-действий;
- команда и документация явно показывают риск.

Проверь два последовательных вызова и отказ. Не считай env-переменную,
подтверждающий флаг или секретную строку permission-gate: автономный агент может
выставить/повторить их сам. Барьер должен жить в harness, а не в логике агента.

## 6. Страховка от расползания

Добавь проверку, которая падает, если тестовый файл (или эквивалентная suite)
не имеет ровно одной категории или имеет больше одной. Запусти её в CI. Это не
заменяет безопасный default и не должно превращаться в молчаливое присвоение
категории по умолчанию.

## 7. Отвергнутые варианты

Не предлагай заново:

- правило только в `CLAUDE.md`/docs — это рекомендация, а не запрет;
- env-флаг вроде `PROJECT_LIVE=1` — агент выставит его сам;
- секретную строку подтверждения — показанное один раз подтверждение можно
  повторять без новой остановки.

Обход всё ещё возможен: кто-то может написать собственный скрипт в обход шлюза.
Это явное читерство, а не бездумный запуск стандартной команды. Честно укажи
это ограничение; цель — устранить случайное выполнение боевых действий, а не
построить криптографическую тюрьму.

## 8. Приёмка

Перед отчётом проверь:

- bare test command и CI не собирают ни одного live-теста;
- каждый тест/suite имеет ровно одну категорию;
- не-live тест, дошедший до внешнего клиента, падает до сети;
- локальные данные и логи не изменились (или изменения изолированы в temp);
- danger gateway требует отдельного ask на каждый вызов;
- отказ от ask не производит мутаций;
- явные команды live suite документированы и не запускаются автоматически.

В отчёте разделяй подтверждённые факты, допущения, непрогнанные проверки и
ограничения. Примеры hhru можно упомянуть как иллюстрацию, но решение должно
быть применимо к другому языку, runner-у и внешнему сервису.
