# /fix — багфикс по строгому TDD

Конвейер, превращающий «проходит ревью» в «доказанно правильный». Каждый шаг — с
доказательством; нет доказательства — шаг не пройден.

## Принцип

Сначала **воспроизвести** баг тестом, потом чинить. Это убирает класс «первый фикс
пропустил edge case» (из опыта: `#1249` поймал `DatabaseBusyError`, но пропустил сырой
`sqlite3.OperationalError` на read-пути). Тест пишется ДО фикса — иначе он не ловит
регрессию, а лишь подтверждает текущее поведение.

## Определи тулинг по проекту

- Python (есть `pyproject.toml` / `pytest` / `requirements.txt`): тесты `pytest`, линтер
  `ruff check --fix`, mutation `mutmut run` (или `cosmic-ray`).
- Иначе: определи по файлам проекта (package.json → npm test + eslint/biome; go.mod → go test;
  Cargo.toml → cargo test; и т.п.). Если неоднозначно — спроси у пользователя одну вещь:
  какой тест-раннер.

## Шаги

### 1. Воспроизвести баг (КРАСНЫЙ тест)
- Напиши тест, который воспроизводит ровно описанное поведение (ошибка/неверный вывод).
- Запусти **только этот тест**. Он **обязан упасть** (red) с той же симптоматикой.
- Если тест не падает — ты не воспроизвёл баг. Перепиши, пока не воспроизведёшь.
- Покажи пользователю: команда + фрагмент вывода с фактом падения.

### 2. Минимальный фикс
- Внеси **минимальное** изменение, переводящее красный тест в зелёный.
- Не трогай ничего сверх необходимого. Рефакторинг — отдельной задачей.

### 3. Зелёный
- Запусти тот же тест. Он проходит (green).
- Запусти **всю** релевантную тестовую подсистему (модуль/пакет), чтобы не сломать соседей.
- Покажи: команда + результат (pass count).

### 4. Mutation-проверка (доказать, что тест ловит регрессию)
- Python: `mutmut run --paths-to-mutate <файлфикса>` (или явно по функции). Если mutmut
  не установлен — предложи установить, но не пропускай молча: скажи пользователю, что
  mutation не прогнан, и почему.
- Суть: мутант (изменение в фиксе) должен убиваться твоим тестом. Выживший мутант = тест
  слабый, усили тест.
- Если mutation нереалистичен (внешний сервис, slow test) — явно отметь это и двигайся дальше.

### 5. Линт
- Python: `ruff check --fix .` (ловит unused imports, B009 getattr и т.п. — частый источник
  лишних ревью-витков).
- Покажи, что ruff чист (или что пофиксил).

### 6. Коммит — с проверкой committed ≠ staged
Это шаг, на котором чаще всего врут «PR-ready, а на деле только staged».
- Закоммить изменения.
- **Обязательно проверь**, что изменения реально в коммите, а не только в индексе:
  ```bash
  git status --porcelain   # должен быть чист (или без твоих файлов)
  git log --oneline -1     # твой коммит сверху
  git show --stat HEAD     # файлы реально в коммите
  ```
- Если `git status` показывает твои файлы как staged/modified — коммит не прошёл, НЕ
  сообщай «готово». Разберись и закоммить по-настоящему.
- Сообщение коммита: `fix(<scope>): <что> — <red→green доказательство>`.

### 7. PR с зелёным CI
- Запушь ветку, открой PR (название, тело со ссылкой на issue, краткое red→green).
- **Дождись зелёного CI.** Не сообщай «PR готов», пока checks не зелёные.
- **Не мержи.** (Мерж — отдельное решение пользователя/cycle-review.)
- В финальном отчёте: номер PR, commit SHA, статус CI (зелёный), краткое mutation-доказательство.

## Что доложить пользователю в конце

- issue/баг: что было.
- красный тест: файл + строка, что упало.
- фикс: файл + суть изменения (1–2 строки).
- зелёный: tests passed (N).
- mutation: прогнан/не прогнан (с причиной), выживших мутантов.
- ruff: чист.
- коммит: SHA (подтверждено committed, не staged) — с доказательством `git show`.
- PR: номер, CI = green, не слит.

## Антипаттерны

- Не писать тест «под фикс» (сначала фикс, потом тест) — такой тест не ловит регрессию.
- Не сообщать «готово» без `git status`/`git log` — staged≠committed.
- Не мержить.
- Не пропускать шаг молча; если шаг невозможен (нет mutation-тула) — сказать это явно.
